## Design decisions
- **Masking goes inline in `CREATE OR REPLACE VIEW`, not a separate `ALTER VIEW`.**
  - Each view is created with its masking in one atomic statement, so a view never exists unmasked.
  - The script can be re-run safely. A `CREATE OR REPLACE` followed by `ALTER` would briefly drop the policies.
  - I'll update the card, which currently says `ALTER`.
- **Regular views, not secure views.** How each source column maps to a business name is part of the demo story, and masking does the protecting.
- **Columns** are renamed pass-throughs, so the source types are kept. This matters because policy input types must match, e.g. `NUMBER(12,2)` and `NUMBER(15,2)`.
