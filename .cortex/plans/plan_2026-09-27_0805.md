## Design
- **Three procedures with an identical body;** only the name and the owner differ. That makes the demo point directly: same code, same rows, different visibility.
- **`PERSONA` comes from `REPLACE(CURRENT_ROLE(),'_ROLE','')`,** not a hard-coded string. If ownership or owner's rights were wrong, it would come back as `ACCOUNTADMIN` and the tests would fail, so the column proves itself.
- **Rows are chosen deterministically:** the first 3 primary sourcing rows by `part_id`, with their part and supplier, paired by rank with the first 3 customers by `customer_id`. All three personas therefore get the **same IDs** and differ only in the masked values.
- **Procedure definition:** `LANGUAGE SQL`, `EXECUTE AS OWNER`, and `RETURNS TABLE(...)` with explicit types (`UNIT_COST`/`CONTRACT_PRICE` `NUMBER(12,2)`, `CREDIT_LIMIT` `NUMBER(15,2)`, the rest `VARCHAR`). The body returns `TABLE(resultset)`.
- **Ownership:** created as `ACCOUNTADMIN`, then `GRANT OWNERSHIP ... TO ROLE <persona> REVOKE CURRENT GRANTS`, then `GRANT USAGE` to `FORGE_ADMIN`, the app owner.
