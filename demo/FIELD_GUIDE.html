The big picture

Supply Chain Forge makes sure every team in a company gets the same answer to the same business question, and lets anyone ask that question in plain English.

Planning says68.2%on-time delivery, counted against the ERP order date
same
shipments
Logistics says87.5%counted against the carrier's promised date. This becomes the one governed answer.
In plain words

A company keeps its data in four separate systems. Each one names and dates things its own way, so two teams asking "what is our on-time delivery rate?" get numbers 19 points apart. Nobody trusts either.

This project fixes it by cleaning the data, protecting the sensitive parts, and writing down each business term exactly once, in one place called a semantic view. Every screen, every person and the AI agent read from that one definition, so they all get the same number.

The one line to remember

Define every business term once, in code. Make every consumer, human or AI, read that one definition.

~6Mrows of realistic, deliberately messy data
4canonical metrics, plus 15 supporting ones
3business roles with different masking
28/30agent evaluation questions correct
~1 sfor known questions, with no AI call

Analogy

Think of a water system. The source is river water. The cleaning layer is the treatment plant. The governed layer is the pipe network with valves that decide which house gets which supply. The semantic view is the meter that everyone agrees measures a litre the same way. The consumers are the taps.

Reuse it anywhere

This layering (raw → clean → governed → semantic → consumers) works on any data platform. The rule that makes it work: each layer reads only from the one above it, and the app reads only from the top two. If an app ever reads raw tables, two screens will eventually disagree.

The data layers · Source

Messy source systems

Four systems, built to look and behave like real enterprise software, including the mess.

In plain words

Real companies don't have one tidy database. Sales lives in the ERP, stock in the warehouse system, deliveries in the transport system, suppliers in procurement. Column names are cryptic (ERDAT, LABST, PROM_DLV_DT), and the data has duplicates, typos and test rows. A demo with clean data proves nothing, so this project generates realistic messy data on purpose.

The mess catalogue: 19 kinds of real-world defects

Repairable defects

Re-sent duplicates, out-of-date status versions, code variants (Apac, ASIA-PAC, CNL), test and dummy records, non-USD amounts, late arrivals, ID whitespace and case problems.

Business-rule edge cases

Missing promised dates, orders cancelled after shipping, returns, over-shipments, negative stock, zero usage, outlier costs, orphan rows, ERP/TMS date conflicts, future-dated orders.

A deterministic generator

The data comes from a Snowflake procedure with a fixed seed (20260929). Every "random" choice is a hash of the seed and the row, so running it twice gives byte-identical data. That made it possible to move the whole project to a new Snowflake account and prove nothing changed, with a checksum over all ten tables.

data_gen/10_sp_generate_data.sql (the idea)
-- a "random" number between 0 and 1 that is always the same for this seed and row
BITAND(HASH(:SEED, 'VTTK', tknum, 'A03c'), 4294967295) / 4294967295.0
Analogy

A flight simulator. Pilots don't train on perfect weather; the simulator throws storms, engine faults and bad radio at them on purpose, and the same scenario can be replayed exactly.

Reuse it anywhere
  • Test with dirty data on purpose. Write down the defects you expect (a "mess catalogue"), inject each at a known rate, and check your cleaning removes exactly that many.
  • Make generators deterministic. Use a seed and hash-based randomness (or random.seed() / Faker's seed) so tests and demos are reproducible.
  • Keep raw data raw. Never fix data in the source tables. Fix it in the next layer, so you can always see what came in.
The data layers · Conformed

The cleaning layer

Ten dynamic tables turn the messy source into clean rows, and keep them clean as new data arrives.

In plain words

A dynamic table is a table defined by a query. You write "this table is the clean version of that table", and Snowflake keeps it up to date by itself, processing only the rows that changed. You declare the result you want; the platform works out how to refresh it.

1
Keep the latest versionSystems re-send rows. Keep only the newest version of each ID (QUALIFY ROW_NUMBER() … = 1).
2
Map codes to one standardA CODE_MAP table turns every variant (DHL Express, dhl_exp) into one canonical code.
3
Convert money to USDJoin each amount to the exchange rate of its own date.
4
Drop what doesn't belongTest records, orphan rows with no parent, out-of-scope orders.
5
Flag, don't hideImplausible costs become NULL and every repaired row carries dq_flags saying what was fixed.
sql/04_governance/06_conformed_layer.sql (shortened)
CREATE OR REPLACE DYNAMIC TABLE CONFORMED.SHIPMENT
    TARGET_LAG = '1 day' WAREHOUSE = FORGE_WH REFRESH_MODE = INCREMENTAL
AS
WITH s AS (
    SELECT * FROM TMS_SOURCE.VTTK
    -- keep only the newest version of each shipment
    QUALIFY ROW_NUMBER() OVER (PARTITION BY UPPER(TRIM(TKNUM)) ORDER BY LOAD_TS DESC) = 1)
SELECT UPPER(TRIM(s.TKNUM))                         AS shipment_id,
       COALESCE(carrier_map.CANONICAL, s.CARRIER_CD) AS carrier,      -- one code per carrier
       s.PROM_DLV_DT                                 AS promised_delivery_date,
       ROUND(s.FREIGHT_AMT * fx.usd_rate, 2)         AS freight_cost  -- in USD
       ...
Analogy

A spreadsheet formula. You don't recalculate the total column by hand every time a number changes; you write the formula once and the sheet keeps it right. A dynamic table is that, for a whole table.

Reuse it anywhere
  • Declarative, incremental pipelines exist everywhere: dbt incremental models, Postgres materialized views, Databricks Delta Live Tables, BigQuery materialized views.
  • The medallion naming (bronze → silver → gold) is the same idea as source → conformed → governed.
  • The five cleaning steps above are a checklist you can apply to any messy dataset.
  • Flag instead of silently fixing. A dq_flags column lets analysts see and count every repair.
The data layers · Governed

Governance & masking

Three roles see different details of the same data, and the database itself enforces it, not the app.

In plain words

A masking policy is a small rule attached to a column: "if the person asking has this role, show the real value; otherwise show *** MASKED ***". Because the rule lives in the database, every tool that reads the column gets the same protection: the app, the AI agent, a spreadsheet export.

Production Planner0.875448

  • Unit cost
  • Payment terms
  • Credit limit
Procurement Lead (Buyer)0.875448
  • Customer names
  • Unit cost
  • Payment terms
  • Credit limit
Logistics Coordinator0.875448
  • Customer names
  • Unit cost
  • Payment terms

Same on-time delivery rate, to six decimals, for all three, while each sees different columns. (The exact number moves a little as new days are added.)

sql/04_governance/02_masking_policies.sql
CREATE OR REPLACE MASKING POLICY MASK_CUSTOMER_PII AS (val VARCHAR)
RETURNS VARCHAR ->
    CASE
        WHEN CURRENT_ROLE() IN ('FORGE_ADMIN', 'PLANNER_ROLE', 'LOGISTICS_ROLE') THEN val
        ELSE '*** MASKED ***'   -- the buyer sees this instead
    END;

Three more governance ideas used here

  • Business names. VTTK.PROM_DLV_DT becomes V_SHIPMENT.promised_delivery_date. People and the AI read meaning, not codes.
  • One authoritative date. The ERP's own "promised" date is simply not exposed. The disagreement from chapter 1 can't come back, because the wrong column doesn't exist in this layer.
  • Tags. Every column carries a tag such as SEMANTIC_ROLE = 'KEY' or a sensitivity level, so tools can find sensitive data automatically.
  • Persona procedures. SP_METRICS_AS_PLANNER() (and the Buyer and Logistics versions) are owned by each role and run with the owner's rights, so the app can prove "what each role sees" without logging in as three people.
Reuse it anywhere
  • Postgres: views that expose only safe columns, column privileges, and row-level security policies (CREATE POLICY).
  • BigQuery: policy tags and dynamic data masking. Databricks: Unity Catalog column masks and row filters.
  • The principle: put access rules in the data platform, not in application code. An app check protects one app; a database policy protects every way in.
  • Remove the wrong column instead of documenting "don't use it". If it isn't there, nobody can use it by mistake, including an AI.
The data layers · Semantic

The semantic view

The heart of the project. One object that holds the business meaning of the data: the ontology.

In plain words

A database knows tables and columns. A business thinks in things (orders, shipments, suppliers), how they connect (an order has many lines; a shipment belongs to one order) and measures (on-time delivery, fill rate). A semantic view writes that business vocabulary down in code, on top of the tables. Everyone who asks a question, person or AI, speaks this vocabulary instead of writing raw SQL.

semantic/01_semantic_view.sql (shortened)
CREATE OR REPLACE SEMANTIC VIEW SEMANTIC.SUPPLY_CHAIN_SV
  TABLES (
    shipments AS GOVERNED.V_SHIPMENT PRIMARY KEY (shipment_id)
              WITH SYNONYMS ('delivery', 'consignment'),
    orders    AS GOVERNED.V_ORDER    PRIMARY KEY (order_id) ...
  )
  RELATIONSHIPS (
    shipments_to_order AS shipments (order_id) REFERENCES orders ...
  )
  DIMENSIONS (
    shipments.carrier AS carrier WITH SYNONYMS ('transporter') ...
  )
  METRICS (
    shipments.on_time_delivery_rate AS
      COUNT_IF(actual_delivery_date <= promised_delivery_date)
        / NULLIFZERO(COUNT_IF(actual_delivery_date IS NOT NULL
                              AND promised_delivery_date IS NOT NULL))
      WITH SYNONYMS ('OTD', 'on time delivery')
      COMMENT = 'Share of delivered shipments arriving on or before the TMS promised date...'
  )
  AI_SQL_GENERATION 'Rules for every query on this view. 1. Use the named metrics...'

How you query it

You ask for metrics and dimensions by name. You never write the joins or the formula; the view does.

the pattern the app uses
SELECT * FROM SEMANTIC_VIEW(
    SUPPLY_CHAIN_FORGE.SEMANTIC.SUPPLY_CHAIN_SV
    DIMENSIONS plants.plant_region
    METRICS    shipments.on_time_delivery_rate
    WHERE      shipments.ship_date > DATEADD(month, -12, CURRENT_DATE())
);
Analogy

A restaurant menu. Customers order "the chicken curry" by name; they don't walk into the kitchen and list ingredients. The recipe (the formula) is written once, by the chef, and every order of that dish tastes the same.

Reuse it anywhere: the most portable idea in the project
  • Tools that do this outside Snowflake: dbt Semantic Layer (MetricFlow), Cube, Looker's LookML, Power BI semantic models, AtScale.
  • Without any tool: keep a YAML or JSON file of metrics (name, formula, synonyms, valid dimensions, default window) and have your app build SQL from it. That is already a semantic layer.
  • For AI projects: give the LLM the semantic layer instead of raw tables. It picks from named metrics instead of inventing formulas, which is far more accurate.
  • Synonyms pay twice: they help people search and they teach the AI your company's words.

Metrics & the time rule

Four canonical metrics, each with one formula, one default time window, and clear rules for edge cases.

MetricFormulaDefault windowValue*
On-time deliveryDelivered on or before the TMS promised date ÷ delivered shipments with a promised dateShipped in the last 12 months87.5%
Fill rateQuantity shipped ÷ quantity ordered, on shipped or delivered ordersOrdered in the last 12 months92.6%
Days of inventoryAverage stock on hand ÷ average daily usageThe latest stock snapshot36.4 days
Average landed costAverage of freight + duties + handling per shipment, in USDShipped in the last 12 months$604.84

*Captured 29 Sep 2026. The window moves with today's date, so values drift slightly day to day.

What a complete metric definition includes

"Fill rate = shipped ÷ ordered" sounds finished, but two teams can still disagree. A definition is only complete when it answers these questions:

  • Which rows count? Fill rate ignores OPEN and CANCELLED orders (they haven't had a chance to ship).
  • What about missing values? On-time delivery leaves out shipments with no promised date, from both the top and the bottom of the fraction.
  • What about strange values? Over-shipments count as fully shipped. Negative stock counts as zero. Implausible costs are excluded.
  • Which period by default? The time rule: last 12 months by ship date for shipment metrics, by order date for order metrics, the latest snapshot for inventory.
  • Which date column? Ship date, not order date, for shipments. One choice, written down.
NULL is a real answer

If a plant has only open orders, its fill rate is not 0% and not 100%. There is nothing to measure, so the answer is NULL, shown as "—". Formulas use NULLIFZERO on the bottom of the fraction so an empty group gives NULL instead of an error or a fake zero.

Reuse it anywhere

Use the five questions above as a metric definition checklist on any project: rows in scope, missing values, odd values, default period, which date. Write the answers next to the formula. Most "why don't our numbers match?" meetings are one of these five, unanswered.

The fan-out trap

Some breakdowns quietly count the same rows twice. The project refuses them on purpose.

In plain words

An order can have several lines (parts) and several shipments. If you join shipments to parts, each shipment appears once per part on its order. Count shipments after that join and you count some shipments two or three times. The query runs without error and gives a wrong number. That silent mistake is the fan-out trap.

One order

LinesShipments
Bolt, GearS1 (on time), S2 (late)
Truth: 2 shipments, 1 on time → 50%

Shipments joined to parts

PartShipment
BoltS1, S2
GearS1, S2
4 rows. "Shipments" = 4. Wrong.

Shipments by plant

PlantShipment
Tokyo DCS1, S2
2 rows. 50%. Correct.
Metric familySafe to break down byRefused (fan-out)
On-time delivery, landed cost, shipment countsPlant, region, carrier, shipment status, order attributes, customerPart, part category, supplier
Fill rate, revenue, unitsPart category, plant, order attributes, customerCarrier, shipment status, ship date
Days of inventoryPlant, part, snapshot dateAnything about orders, shipments or customers (no path)

How the project guards against it, in three places

  • The contract lists every valid metric-and-dimension pairing (and the app's router only offers those).
  • The semantic view's AI instructions tell the agent to refuse these breakdowns and offer the nearest valid one ("not by part, but I can show it by plant").
  • The app shows a visible warning if an AI answer ever pairs a metric with a dimension the model doesn't support.
  • One fix in the model: parts have many suppliers, so "fill rate by supplier" would fan out. A primary_sourcing table keeps exactly one supplier per part, making that breakdown safe.
Reuse it anywhere

Before trusting any breakdown, ask: "does this join turn one row into many?" If a one-to-many join sits between the metric's table and the dimension, the numbers are inflated. Count rows before and after the join, list valid pairings next to your metrics, and teach your AI to refuse the rest.

Asking questions

The Cortex Agent

An AI that reads a plain-English question, picks a tool, gets governed data, and writes the answer.

In plain words

The agent is a language model with two tools. It doesn't know the data itself. For every number it calls a tool, reads the result and writes the answer from that result. It never computes or guesses a number on its own.

Two kinds of instructions

Orchestration instructions

What to do. Which tool for which question, when to refuse (out of scope, restricted data, impossible breakdowns, write requests), when to ask a clarifying question, the time rule, one tool call per question part.

Response instructions

How to write it. Start with the direct answer and its period, list every row up to 10 as "- name: value", number formats, bold headings for multi-part questions, never include restricted values.

Lessons learned (real bugs from this project)
  • "Keep answers brief" truncated lists. Asked for the top 5 suppliers, the agent said "led by X and Y" and stopped. A style rule can silently drop data. The fix: "list every row the question asks for".
  • Don't let the agent draw charts. A built-in chart skill added 15–20 seconds per answer. The app draws charts from the result rows instantly, every time.
  • Editing in a web form broke a tool. Saving the agent from the console form changed its tool settings. The agent's whole definition lives in one SQL file, and re-running that file is the only way it is changed.
  • Speed comes from fewer steps. SQL ran in 0.07 s; almost all of the ~12 s was the model thinking. One tool call per question, no re-checking, and no charts were the real speed-ups.
Reuse it anywhere
  • Agent = model + small set of tools + instructions. The same shape works with Claude's tool use, OpenAI functions, LangGraph or any framework.
  • Ground text-to-SQL in a semantic layer, not raw tables. The model chooses named metrics instead of inventing joins.
  • Split "what to do" from "how to write it" in your prompts, and test both.
  • Keep the agent's definition in version control and deploy it from there.
Asking questions

Instant answers

A small rule-based router answers known questions in about a second, without calling the AI at all.

In plain words

Most questions people ask are the same few: "what is our fill rate?", "on-time delivery by region". Sending those to an AI costs money and takes 10+ seconds. The router recognises them with simple word matching and runs the semantic view's own verified SQL directly. Anything it isn't sure about goes to the agent.

1
Split the question"1. What is our fill rate? 2. Days of inventory by plant?" becomes two parts (numbered parts, "?", ";" or "A and B"; up to 4).
2
Match each partExactly one canonical metric, at most one valid breakdown or one value ("OTD for enterprise customers"), and no other words.
3
Forgive small typos"fil rate" still matches "fill rate" (fuzzy match, 0.85 similarity cut-off).
4
Anything unknown goes to the agentA period, a number, "why", an unknown name. Better a slower right answer than a fast wrong one.
5
Agent parts run in parallelA three-part question with two AI parts waits for the slowest part, not the sum.

Its vocabulary comes from the semantic view

The router's words are not hand-typed. A build script reads the semantic view's names, synonyms and descriptions and writes vocabulary.json. Add the synonym "haulier" to the carrier dimension in Snowflake, rebuild, and the app understands "OTD by haulier" with no code change. Plant and carrier names are learned from the view's own results.

Say it like this

"The router never computes a number. It only decides which governed road answers, and its SQL is the semantic view's own verified query, text for text. On our 30 evaluation questions it took zero wrong shortcuts."

Reuse it anywhere
  • Put a deterministic fast path in front of every LLM. FAQ matching, intent rules, or cached answers handle the common 60–80% instantly and for free.
  • Make the fast path conservative: when unsure, hand off. Measure false shortcuts on an evaluation set.
  • Generate the vocabulary from your source of truth (semantic layer, schema, CMS) so it never drifts.

Answers, charts & streaming

Every answer shows its working, and the data behind it is always on screen.

The app draws charts, not the AI

The app looks at the result columns, picks a label column (a name, a region, a period) and a measure column (a number that isn't an ID or a date), and draws bars, or columns for time periods. Rows it can't chart (names only, a single order lookup) become a clean table. The data can never vanish from the card because of how the AI phrased its text.

Streaming

For a single AI question, the app calls the agent's streaming API (server-sent events) and shows the agent's status line and its words as they arrive, with a Stop button. If streaming fails before it starts, the app quietly falls back to the normal one-shot call. If it fails halfway, the partial answer is kept, marked incomplete and never cached.

Reuse it anywhere
  • Show the working: SQL, definitions and sources build trust in any AI answer.
  • Render data deterministically from structured results; let the LLM write words only.
  • Stream long answers with a status line and a stop button; plan the fallback and the half-finished case.
Trust & operations

Data quality checks

77 automated checks watch every load, so a bad load is caught before it reaches an answer.

In plain words

A Data Metric Function (DMF) is a small check attached to a table: "count duplicates", "count rows with no promised date", "count orphan lines". Snowflake runs it whenever the table changes and stores the result. If the clean layer ever shows duplicates again, a check turns red.

CheckOn the clean layerOn the raw layer
Duplicate records0 passing190,425 expected
Non-standard codes0 passing106,811 expected
Orphan order lines0 passing4,149 expected
Missing promised dates5,539 for information6,212 expected

Checks run on both layers: the raw numbers prove the mess is real; the clean numbers prove the cleaning works.

The data-health procedure

SP_DATA_HEALTH('ALL') returns, for each entity: rows, latest load time, freshness (OK under 36 hours, WARN under 72, FAIL after), and any check that isn't OK. It feeds three places: the Data health screen, the agent's data_health tool, and an alert that emails if data turns stale.

Reuse it anywhere
  • Tools: dbt tests, Great Expectations, Soda, or plain scheduled SQL that writes results to a table.
  • Check both layers. Raw-layer counts document the problem; clean-layer zeros prove the fix.
  • Expose freshness ("data as of …") everywhere a number appears. People trust what they can date.
  • Separate "failing" from "for information". Not every non-zero is an error.

A procedure sends every question to the agent and grades each answer automatically. Run it after every change to the agent, and you know if you made it better or worse.

Fresh data every night

A scheduled task adds one new business day every night, so the demo is never frozen in time.

The app noticesCaches are keyed on the data's as-of date, so new data means new answers automatically.
Reuse it anywhere
  • Idempotent jobs: running the same day twice writes nothing the second time.
  • Append, don't update: keep history as row versions; the clean layer picks the latest.
  • Key caches on data version, not just on time, so a refresh can never show stale answers.
How it was built

Two agents, one contract

Two AI coding agents built the project in parallel, coordinated by a human, against one frozen interface document.

Agent 1CoCo CLIBuilt and ran everything in Snowflake
↔
ArbiterCONTRACT.mdEvery name, metric, pairing, masking rule
↔
Agent 2Claude CodeApp, tests, docs, generator SQL

How the parallel work stayed in sync

  • The contract is frozen. It fixes every object name, metric formula, valid pairing, masking rule and query pattern. Both agents build to it without waiting for each other.
  • Changes go through change requests. When reality differed (a Snowflake limitation, a better design), an agent appended a numbered change request, and the human approved it.
  • The handoff lock. Claude Code wrote SQL but had no Snowflake credentials. It added each file to a "ready to run" table and stopped editing it; CoCo ran it and wrote a run report with exact results and errors.
  • Captured artifacts. Real Snowflake outputs were saved as files, and the app's tests replay them, so the app is tested against reality without a database.
  • One task card per track, with a gate that must pass before it counts as done.
Reuse it anywhere

This works for human teams too: contract first (agree the interface before building), change requests instead of silent drift, run reports with exact outputs, and recorded real responses to test against. With several AI agents it is essential, because they don't share memory.

One data module

Only one file in the app talks to Snowflake. Every function in it has a mock branch and a live branch, and one switch chooses. That single seam is what makes the three modes possible.

Reuse it anywhere
  • Put all external calls behind one module with a mock and a live implementation.
  • Record real responses once, replay them forever in tests.
  • Write tests for your rules, not just your code: "no secret in the repo", "the agent file grants the app role", "no tool returns cost".

Glossary

Every term in this guide, in one or two plain sentences.

OntologyThe business entities, how they relate, and what their measures mean. Here, it is the semantic view.
Semantic view / semantic layerA layer that names business entities, joins and metric formulas once, so every consumer uses the same definitions.
Canonical metricThe one official version of a measure, such as on-time delivery.
DimensionSomething you group or filter by: region, carrier, quarter.
FactA row-level number, like a shipment's freight cost.
GrainWhat one row means: one order, one order line, one shipment. Mixing grains causes fan-out.
Fan-outA join that repeats rows, so a count or sum is inflated without any error.
Dynamic tableA Snowflake table defined by a query and kept up to date automatically, refreshing only what changed.
Target lagHow out of date a dynamic table may get before it refreshes (here, 1 day).
Masking policyA rule on a column that shows the real value only to allowed roles.
Role (RBAC)A named set of permissions. People and apps act as a role.
Owner's rights procedureA stored procedure that runs with its owner's permissions, not the caller's.
Cortex AnalystSnowflake's text-to-SQL service that writes queries against a semantic view.
Cortex AgentSnowflake's AI agent: a model that plans, calls tools such as Analyst, and writes the answer.
Verified queryA known-correct SQL answer to a common question, stored in the semantic view.
OrchestrationThe agent's planning step: which tool to call, and in what order.
SSE (server-sent events)A one-way stream from server to browser, used to show an answer while it is written.
DMF (Data Metric Function)A data-quality check attached to a table, run automatically when the table changes.
FreshnessHow long ago the newest data arrived.
Evaluation setQuestions with known correct behaviour, used to grade an AI automatically.
p50 / p95The median answer time, and the time 95% of answers beat.
Key-pair authenticationLogging in with a private key instead of a password.
IdempotentSafe to run twice: the second run changes nothing.

Explain it to anyone

What to say in 30 seconds, and answers to the questions people ask.

The 30-second version

"Supply chain data lives in four systems that disagree. Ask for on-time delivery and Planning says 68%, Logistics says 87.5%, on the same shipments. I built a governed semantic layer in Snowflake that defines every metric once, with masking per role, and a Cortex Agent on top. Now the planner, the buyer and the logistics coordinator get the identical number, to six decimals, while each sees only the details they're allowed to. Anyone can ask in plain English; common questions answer in a second without AI, everything else through the agent."

Why not just fix the dashboard?

Because the disagreement isn't in one dashboard. Every tool and every team writes its own SQL. Fixing it once, in a shared semantic layer, fixes it for every consumer, including the AI.

How do you stop the AI from making numbers up?

It can't compute anything itself. Every number comes from a tool that runs SQL on the semantic view, which holds the official formulas. The app also draws charts from the actual result rows, not from the AI's text.

Why is masking in the database and not the app?

So it protects every way in. The app, the agent and a raw SQL query all hit the same policy.

How do you know the agent is good?

A 30-question evaluation set graded automatically (28/30), plus 10 adversarial attacks (10/10), run after every change.

Would it scale to real data?

The heavy lifting is incremental dynamic tables and Snowflake's own engine; SQL ran in 0.07 seconds on the smallest warehouse. Replacing the generator with real SAP connectors leaves every layer above unchanged.

What would you do next?

Real source connectors, more metrics in the semantic view, saved conversation history, user feedback on answers, and enterprise sign-in so each user's own role applies directly.

What's the most reusable idea?

Define every business term once, in code, and make every consumer, human or AI, read that one definition. It works with or without Snowflake.
